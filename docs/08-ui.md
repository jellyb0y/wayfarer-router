## The central problem: forms for protocols nobody has modelled

The extensibility argument in [04-tunnels-and-protocols.md](04-tunnels-and-protocols.md)
only holds if the interface can render a protocol it has never heard of. Otherwise
the schema is a nice idea and every new protocol still needs a form.

Worth knowing: of the projects surveyed, **none** generates forms from a schema.
They all use schemas for editor autocompletion and write forms by hand, per
protocol. So this is the one place where the design has no prior art to copy, and
it deserves care rather than optimism.

### Why not a generic form library

Libraries that render JSON Schema exist. They struggle precisely where our schema
is hardest: outbounds are a `oneOf` of 21 branches, and generic `oneOf` handling
either asks the user to pick a branch by index or tries to infer it by validating
against each.

We do not have that problem, because we know the discriminator. Outbound branches
are distinguished by a `const` on `type`. So:

**Resolve the `oneOf` ourselves, then render a flat field list.**

### Correction: the union is nested, and `type` is not unique

An earlier revision of this document described the union as flat and discriminated by a
single `const`, and said the resolver picks "the branch whose type const matches". Both
halves are wrong on the binary this project actually runs against, and the wrong
reasoning is worth keeping because it is the assumption anyone would make: a
discriminated union is normally flat, and a discriminator normally identifies one branch.

Measured against `sing-box schema` from the bench board (1.14.0, 444 895 bytes, 93
`$defs`, 2026-09-19):

* **`$defs/Outbound.oneOf` has 20 entries, and entry 11 is itself a `oneOf`.** Flattened,
  the union is 21 branches. A resolver that reads one level finds 20 and silently loses
  one.
* **`snell` occupies two of those branches**, separated by a second `const`
  (`version: 4` on one of them). So a single-key lookup returns the *first* match, which
  is the wrong field list for half the configurations of that protocol — and the failure
  is a form that looks correct and rejects what the user types.

What the resolver does instead: flatten `oneOf` and `anyOf` recursively, then, when the
discriminator selects more than one branch, find a property whose `const` differs across
them and use it as a secondary discriminator. **If no such property exists it refuses**,
naming the type, rather than taking the first. Guessing produces a form that is wrong in
a way nobody can see; refusing produces a message somebody can act on.

The resolver is tested against the unmodified 444 895-byte schema rather than a hand-made
miniature, because neither of the two properties above can be reproduced by one.

### Where labels for a secret come from

The same schema contains **no `x-secret` annotations either** — zero, alongside its zero
descriptions and zero titles. That is a security gap rather than a cosmetic one, and it is
addressed in [10-security.md](10-security.md): the annotation is stamped onto the foreign
schema from the overlay *and* from a name rule, unioned, and the union fails towards
redaction. The consequence visible in the interface is that a field unluckily named like a
secret renders as a write-only password field, and the operator re-enters a value that
never needed protecting.

```
schema + selected type
      │
      ▼  resolve: flatten the nested oneOf, match type (plus a secondary
      │           const when type is ambiguous), inline its $refs
  flat field descriptors
      [{ pointer, jsonType, enum?, default?, min?, max?, required,
         secret?, tagReference? }]
      │
      ▼  overlay: merge metadata by pointer
      [{ …, label?, help?, group?, order?, widget?, level? }]
      │
      ▼  render: one small component per widget kind
  form
```

The resolver is perhaps two hundred lines and fully testable against the real
schema. Every widget is a component we control. No dependency whose `oneOf`
behaviour we have to fight.

### The metadata overlay

The schema emitted by the core has no `description` or `title` fields at all — 93
definitions, zero descriptions, zero titles (counted on the bench board's 1.14.0 binary;
an earlier revision here said 94, which was the count from a different build). Labels are therefore ours, and they live in a
separate overlay keyed by JSON Pointer:

```jsonc
{
  "#/outbound/vless/uuid":            { "label": "UUID", "secret": true, "level": "basic" },
  "#/outbound/vless/transport/path":  { "label": "WebSocket path", "level": "advanced",
                                        "help": "Must match the server. Usually /." },
  "#/outbound/*/server":              { "label": "Server", "order": 1, "level": "basic" }
}
```

The property that makes this work: **the overlay is optional, per field.** A field
with no entry renders with its raw schema key as the label, in the advanced group,
with a plain widget for its type. So a protocol released this morning produces a
usable form with no work, and a pleasant form after ten lines of overlay. Degrading
to "usable" instead of "broken" is the whole design goal.

Widgets derive from the schema first and the overlay second: `enum` becomes a
select, `boolean` a switch, `x-secret` a write-only password field showing whether a
value is set, `x-tag-reference` a picker listing the tunnels in the current profile.

### The raw editor — removed in Epic E, 2026-09-21

**There is no raw editor.** Epic E deleted it, and this section is kept for the argument
below rather than as a description of the interface. The escape hatch was the mechanism
that made "a protocol nobody designed a screen for" expressible at all, which is what the
owner objected to; each of the three catalogue entries has a designed screen instead. A
finding in the planner still named this editor as the remedy for an invalid tunnel
configuration, sending a person to a screen that does not exist; that text is corrected.


Every tunnel form has an escape hatch: a JSON editor for the outbound object,
validated live against the core's schema. Useful when a protocol is ahead of our
overlay, when copying a configuration from elsewhere, and for debugging what the
form produced. Switching between form and raw preserves the value in both
directions where it is representable.

### The confirmation window: four properties, each a safety property

This is the only screen whose job is to be correct **while the connection carrying it is being changed**,
which is the ordinary case rather than an exotic one.

1. **Doing nothing is safe, and the page says so before anything is applied.** `NoActionNotice` sits
   immediately above the apply button for a `network` change — not in the consequence panel, because the
   button is where the reader's eyes are when they decide. After the connection goes there is no page left
   to explain anything on.
2. **The countdown is derived from a deadline, never decremented.** A local counter is wrong in exactly the
   case this exists for: a backgrounded tab, a sleeping laptop, a hung request. The deadline it derives
   from is built in the browser from a *duration* the device sent — see
   [06](06-apply-and-rollback.md#the-countdown-the-operator-watches-is-a-duration-not-an-instant).
3. **Losing contact is reported as expected, not as an error**, with the instruction repeated and the
   confirm button disabled — a confirmation has to reach the device to mean anything, and one that appeared
   to work while going nowhere would be worse than none. A countdown that merely freezes teaches the reader
   to reload, and reloading is the one action that cannot help.
4. **It never claims the change was kept** until the device has said so. `unknown` contact is not drawn as
   lost, so the page does not cry wolf every time it opens.

The liveness poll exists only to notice that contact is gone. It never confirms anything, and the confirm
mutation is **never retried automatically** — a retry that succeeded after the operator walked away would
keep a change nobody agreed to.

### The event ring, and what the screen owes the reader

The ring is the **only record on the device that survives a power cut** — the journal
beside it is in RAM and is gone after a reboot. So after exactly the failure anybody
wants to investigate, a board that stopped answering and was power-cycled, this table
is the whole record. Two things follow, and both are on the screen rather than in this
document:

* **What it holds**, named: applies started, succeeded, failed and reverted; profile
  switches; tunnel health changes; safe mode; sign-ins and lockouts; switch-offs asked
  for through the API. Not a request log, not a heartbeat.
* **How far back it goes**, read from the oldest row it still holds rather than
  estimated, together with whether the ring is full. Retention is by *count*, so a busy
  day holds less history than a quiet one — a device that spent an afternoon failing to
  apply a bad profile can evict a week of ordinary history in an hour, right when
  somebody needs what came before. "5000 rows" does not say that.

**Filtering never changes the kept figure.** The rows-kept count always describes the
ring and the match count is reported separately, because a filter that empties the list
*and* zeroes the count teaches the reader that narrowing a view destroys history. An
empty filtered result says so in those words, not as "nothing has been recorded".

Filtering happens on the device, through the parameters the API already has. Doing it in
the browser would mean fetching thousands of rows to show ten, over a link the device may
be about to reconfigure, and would be a second implementation of what `kind` means.

The kinds offered in the filter are **the kinds present in what came back**, not a fixed
list — a fixed list falls behind the kinds the daemon records, and then silently offers
no way to find the newest sort of event.

## Interaction rules

**Editing is local; Apply is explicit.** The editor mutates a draft. A persistent
bar shows how many changes are pending, with Discard and Review. Review calls the
dry run and shows the plan: files changing, units restarting, blast radius,
warnings. This prevents the class of accident where adjusting one field
unexpectedly restarts a tunnel.

**Confirmation is impossible to miss.** After a `network` change the interface shows
a full-width countdown with one primary action, Confirm. The seconds come from the
event stream, so a client that reconnects mid-window picks the countdown up rather
than finding out at second 179. If the page was closed, the next load shows the
pending transaction immediately.

**Impossible configurations are refused where they are made, not at Apply.** The
radio picker knows the interface combinations, so assigning both roles to one radio
is rejected on the spot with the reason. The error contract carries a JSON Pointer
so the message lands on the field.

**Nothing blocks on the network.** Every list renders from the last snapshot and
updates from the stream. A device with a dead uplink still shows its own state
instantly.

## Rebuilt for a person (2026-09-21)

### What is wrong, reported by the owner

Not measured by us, and worth naming as the owner's words rather than our diagnosis:
too many buttons and too much text; text overflowing its container; text wrapping where
wrapping breaks the meaning; forms that do not fit the screen; nothing adapting to a
phone. Every configuration change of the last two days was made through the API, and the
interface was never the faster path for any of them.

That last sentence is the measurement that matters. **An interface that its own authors
route around is not a slow interface, it is an unused one.**

### The prism: one question per screen, on a phone, without a manual

Seven rules, in the order they resolve conflicts.

1. **The phone is the design target, not a breakpoint.** Layouts are built at 360 px and
   given room on a desktop. Not the reverse: a desktop layout squeezed into a phone is
   how the current one overflows.
2. **No horizontal scrolling, ever, anywhere.** A table that cannot fit becomes a list of
   rows, not a table with a scrollbar.
3. **A label is at most three words.** Helper text is one short sentence, and only where
   the label alone would mislead. Anything longer is a document, and belongs in this
   directory rather than on the screen.
4. **A consequence belongs in the control that causes it**, not in a paragraph above it.
   "Block its traffic" is a choice; two paragraphs explaining which loss is smaller is a
   page of this repository.
5. **Advanced settings are collapsed, not absent, and never a different mechanism.** The
   escape hatch is gone; what remains is ordinary fields, some of them folded away.
6. **Long values never break the layout.** Keys, certificates, profile blobs and URLs are
   truncated with a copy control. They are not made to wrap.
7. **Touch first.** Targets at least 44 px, nothing that only appears on hover, no
   control that needs a pointer to discover.

### The screens, and what each answers

| Screen | The one question it answers |
|---|---|
| **Status** (default) | Is it working, and if not, what is wrong? |
| **Tunnels** | What connections exist, which is carrying, what breaks if one dies? |
| **Routing** | What goes where? |
| **Network** | The access point, and the uplink it is using |
| **Clients** | Who is connected? |
| **Events** | What happened, and when? |
| **Settings** | Password, profiles, device |

Seven, each reachable in one tap, each fitting a phone. Status is what opens, because the
question people arrive with is almost always *is it working* — and today that answer is
spread across several pages.

### What gets removed rather than restyled

* The generic form renderer and the JSON escape hatch — see Epic E.
* Every explanatory paragraph in the panel. The reasoning is good and it is not the
  panel's job; it moves here, and the screen keeps the choice.
* Duplicate controls for the same field in different places.
* Any table wider than a phone.

### How this is verified

Not by looking at it on a laptop. **At 360 px, every screen, every form, with the longest
realistic value in each field** — a full OpenVPN profile, a 253-character domain, a
sixteen-tunnel list. The defects the owner reported are all length defects, and a form
tested with short values is a form tested with the wrong values. This is the same rule as
everywhere else here: a test that cannot produce the failure proves nothing.

#### And at 320 px, which is now part of the contract (2026-09-21)

`pnpm --filter @wayfarer/ui run check:360` runs the same check twice, at 360 px and at **320 px**.
Not as a courtesy to an old handset: 320 px is what a 360 px phone becomes at the first step of
browser zoom, which is exactly what somebody does when the text is too small — so the narrower run
is the *same* person on the *same* device, one pinch later.

It earned its place by finding something. Measured before this change: at 320 px the check exited 1
naming **29 elements** past the viewport, all of them `ol.diff > li` — the plan review's sequence,
the one surface a person reads under a countdown. 375 px was clean, which is why nothing had seen
it. The overflow is gone now, and what the narrower run cost to make green is recorded because it is
the useful part: **nothing was shortened for it.** A fold inside a fold stopped indenting twice
below 360 px, and the screen, card, panel and note padding each gave back a few pixels there. The
text that was failing is text the *daemon* writes — a hardware warning about what a radio can do —
and a bench fed shorter values is a bench that proves nothing.

#### What the check measures, after 2026-09-21

Four measurements were added, and each was added because the check was green while the thing it is
named for was false.

* **Break count.** At 360 px, with every existing measurement reporting ok, **299 runs of text
  painted four line boxes or more**: a `span.row-title` of 389 characters as **sixteen lines in a
  222 px box**, four `li` at fifteen, a `p.choice-consequence` at twelve. A box that wraps is a box
  that fits, so nothing could turn the script red. **A length ceiling is not the worst case for a
  layout; a break count is** — the same 200-character string is fine in a card and ruinous in a
  124 px column, and only the browser knows which it is in. The ceiling is **six line boxes**, which
  is what rule 3 costs when it is obeyed: 120 characters paint three lines in a card, and a
  deliberate two-part consequence paints six. A tighter ceiling would have demanded cutting the
  prose this document has already decided must stay, which is how a check acquires an exception
  list.

  A clipped line box is not counted, because it was not painted — an element that actually clips is
  measured inside its own box. Without that the remedy measured worse than the defect: a clamped
  389-character title reported twenty-one lines from a box showing three.

* **Height on arrival**, taken **before** any fold is opened. Opening every fold is right for the
  width measurements and wrong for a height, since a screen with 125 folds open is not a state
  anybody arrives in. Tunnels measured 99 687 px with them open — 128 viewports — and 7 165 px as it
  opens. The ceiling is forty viewports and is deliberately loose: it exists to catch a screen that
  has stopped folding anything, which is a defect with no other symptom.

* **Labels over three words** and **help over one sentence**, which is rule 3 read literally against
  the *rendered* text rather than the dictionary. Before: **5 of 103 labels** over three words, the
  worst at ten — *"If every tunnel stops working, what should this device do?"* — and **57 of 87**
  help and consequence strings over one sentence or 120 characters, the worst at **564 characters
  and four sentences**. After: 0 and 0.

  `HELP_CHARS = 120` is this document's word *short* turned into a number somebody can fail. Two
  strings were judged to need their length and were shortened anyway rather than exempted: the
  leak-policy contradiction, because the two controls it is about each state their own consequence
  directly above it; and the empty-probe notice, which keeps all three of its claims — health
  unknown, watchdog inert, no screen able to say — in 137 characters instead of 213. Nothing was
  exempted, because an exception list is the thing that grows.

Rule 6's remedy is what closed most of the break count: the event summary, the journal line, the
plan-review diff line and a generated routing rule are **values**, and each is cut after three lines
with the whole of it in a copy control. The journal's own note used to argue the opposite — that a
log line is prose and may break anywhere — and it was right about the sentence and wrong about the
page: two hundred lines at ten line boxes each is a pane with no moments visible in it.

### Network prints interface names, because addresses answered the wrong question

Measured on the bench board, 2026-09-21, `ss -tln` on port 8088:

```
127.0.0.1:8088        loopback
10.44.0.1:8088        wlx90de8047b4b4, the access point
192.168.77.8:8088    wfwan0, the wireless uplink
```

and `end0` — the wire, `192.168.77.7/24` — answering nothing. **One subnet, two interfaces,
opposite answers.** A list of addresses cannot express that; read as a list it looks like one
network that works. The name is the only handle a person has on which cable or which radio they are
holding, so the name is what the screen prints and the address is a field of the row.

Three consequences, each a line the screen does not cross.

**It derives the interface, and nothing else.** A bound address is looked up in the kernel's own
address table. Both halves come from the device and it is a lookup, not a judgement. An address that
matches no interface is kept as a row with no name rather than dropped — the panel is audible there
either way, and an address nobody can attribute deserves more attention than one that is attributed.

**It does not classify an interface.** What an interface *is* — wire, access point, uplink, tunnel —
is knowledge about the system with exactly one definition, in the platform layer. Linux reports a
radio as an Ethernet link, so the wire cannot be inferred from what an interface looks like from
here. A second classifier in the browser would read as a convenience and behave as a second source
of truth, agreeing with the device until the day it did not.

**It says which question it cannot answer.** The panel must answer on every local channel and on no
tunnel at all; the negative half is a refusal step in the daemon that records an event when it has
anything to remove, because a refusal means the positive half offered a tunnel — a defect upstream
rather than a lucky save. None of that reaches the browser: `GET /api/system` serves `listen` as a
port, a list of addresses and the names that resolved to nothing. So the one screen where a person
could watch the prohibition work is structurally unable to report the event that says it fired, and
it prints that in those words. **A blank where a refusal belongs reads as "nothing was refused",
which is a claim this device has not made.** The fields needed to fix it are requested of the API,
not worked around here.

### Routing: one editing mechanism, and the pointer that separates two identical words

**The apply flow is a hook, not a screen.** Saving, the plan, the apply and the confirmation window
used to live inside the profile editor, which was correct while that was the only screen that
edited the profile. It is not any more — Routing edits rules, Settings edits the device, the tunnel
editor edits tunnels — and a second copy would have differed from the first in some detail nobody
chose. "Duplicate controls for the same field in different places" is one of the four things this
epic removes; a second *mechanism* for the same act is that defect one floor up. It lives in
`apps/ui/src/lib/editing.ts` and both screens call it.

**Every control carries the JSON Pointer it writes**, as `data-pointer` in the DOM. A rule's domain
suffixes are at `/routing/rules/N/suffixes`; a **tunnel's** are at
`/tunnels/N/resources/domainSuffix` — what that tunnel exists to reach. Same words on screen,
different field underneath, and that collision is how the tunnel's half stayed invisible long
enough to make the product configurable only through the API. So every label on this screen says
*rule*, and the pointer on the control is what makes the two countable as two. It is also what the
coverage manifest is harvested from: the manifest is read off a **rendered** screen, so a field that
leaves the screen leaves the DOM, leaves the harvest, and fails the check by itself.

**The rule editor is a fold, not a private open/closed state.** The first version used its own
accordion, and the consequence was invisible until the bench was run: a control reachable only
through a component's own state is a control the 360 px check cannot reach, so four textareas
holding 253-character values were never measured. Folding it instead put it on the same mechanism
as every other advanced setting — and the bench opens every fold, so it is measured. The fold count
in the check's own output went from 15 to 19, which is the measurement.

**Reordering is two buttons, not a drag.** A drag target is a control that needs a pointer to
discover, and the design target is a phone.

### Settings: the four destinations that became one screen, and the one control that is not on it

The seventh screen holds the password, the profiles, and two folds — **Device** and **Devices**. It
was built last on purpose: each of the things it holds was a navigation entry of its own, and an entry
removed before its replacement exists leaves a capability with no way in at all, which is the defect
this epic deletes rather than a step towards deleting it. So Profiles, Devices and Password each sat
in the bar until the same change that gave them a place here, and the navigation went from eight
entries to six. **Tunnels** is the seventh and arrives with the tunnel editor rather than as an empty
destination.

**The Device fold moved whole, and Status lost it in the same edit.** What the device is made of —
versions, units, interfaces, capabilities, components, hardware warnings — answers real questions and
none of them is *is it working*. It sat at the bottom of Status because there was nowhere else to put
it. Copying it would have been the cheaper edit and the wrong one: two inventories agree until
somebody changes one of them, and the test asserting the move checks **both ends**, because a test on
Settings alone would pass on a copy.

**The aggregate view became a fold, and its three paragraphs are here.** The reasoning that used to be
printed on that page is worth keeping and is not the panel's job:

* There is no controller. This device asks each peer for its own summary with a read-scoped token
  **the peer issued**, and nothing in the fold can apply a change, activate a profile or restart
  anything elsewhere. That is a safety property: the confirmation window protects the operator of the
  device being changed — somebody watching a countdown, able to do nothing and have the change undone
  — and a change arriving from another device has no such operator.
* Reachability has three answers and all three are drawn. A peer that says nothing is **not
  reachable**, which is not the same as being in trouble: the usual reason is that the link between
  here and there is the thing being reconfigured. A peer that answers with a refusal **is working and
  does not accept the credential**. One red row for both sends somebody to the wrong place.
* Two peers reporting one identity almost always means a card was copied, because two installations
  flashed from one image share everything they did not generate themselves. It is reported and nothing
  is changed: deciding which one should get a new identity is not a decision this screen makes.

The six-column table they were printed beside is a row list now, which is also where the widest values
went: the two refusal sentences are row fields, and the pill holds one word. A sentence in a pill
beside a title is what pushed that table past the edge of the screen.

#### There is no “duplicate profile” control, and that is a decision

A copy assembled in the browser has to pull every credential through the page. The full export already
does exactly that and it is deliberately awkward: it needs a separate scope, and it writes a warning
to the event ring, **because it is an operator's considered act**. A button labelled *Duplicate* turns
the same movement into an unnamed routine — somebody presses *make a copy* and carries every
credential they own through a web page without ever reading a sentence that says so. The alternative,
duplicating from the redacted export, produces a copy that cannot be activated until every credential
is retyped by hand.

The correct shape is a copy **inside the store**, where nothing travels and nobody sees the values —
the same move that repairs a damaged profile. That is a route this device does not have, so it is a
new capability and it belongs in [14-open-questions](14-open-questions.md) rather than here. Recorded
in this much detail for one reason: the next person to look at this screen will read the absence as
unfinished work and add the worse of the two versions.

#### Three fields that are not on this screen at all

Device name, time servers and factory reset were in the plan for this screen and left it — the
checking is in [13-plan](13-plan.md). Two of them exist nowhere: `GET /api/system` is read-only and
there is no time-server field in the profile schema. Parity is the requirement and parity is
satisfied, because neither the interface nor the API can set them. Factory reset is deliberately absent
from the API: the panel answers on the wire, on the access point and on the joined network behind a
short published password, and the one action with no undo should not be one request away from anybody
who can reach either network.

**Where the “say it in words” rule stops.** A screen must never leave a blank where an answer belongs
— a screen with nothing where a refusal belongs reports that nothing was refused. The device's name is
*shown*, in the Device fold, beside the version. There is no control next to it and nothing has been
promised, so nothing is explained: the rule is about an absent answer, not about an absent control. A
screen that annotated every fact it cannot edit would grow back the paragraphs this epic is removing.

#### Power: the one control here that acts on the whole device (2026-09-23)

The last card on Settings, below both folds: it is the one act on this screen that cannot be undone
from the panel, and Status answers *is it working* — a question nobody should be one tap from ending.
It is two taps with the same 500 ms floor as deleting a profile (`lib/arming.ts`, now shared, because
a second copy of the number is how one of them comes to be answerable by a double tap again). The
consequence is inside **both** buttons — *Wi-Fi and every tunnel go too; it will not come back on its

While a transaction awaits confirmation the button is disabled and says so, naming the change: the
device would refuse anyway, and a button that let a person press it and then read the refusal is a
button that sends them to find the other screen after the fact. A window that opened between reading
the list and the second tap is refused by the device with a sentence written for a script — eight line
boxes at 360 px, measured — so the card answers that refusal with its blocked state rather than
printing it.

Once the device has accepted, the shell stops asking it anything: the event stream is closed, queries
are cancelled, and every screen is replaced by one panel saying the device is turning off. Every
request after that point is going to fail, and a page that drew each failure would greet the person
who just did the right thing with a wall of red.

The 360 px bench mounts every state of the card, because Settings shows only one of them and the rest
appear only after a tap the bench never makes. `check:360` now also holds a consequential button's
title to the three-word rule and its sentence to the one-sentence rule; before, the first draft's two
sentences inside the button were measured by nothing.

#### A control that is not a profile field carries no pointer

The password, a peer's read token and a new profile's name are not positions in the profile document,

field to the manifest that the schema does not have — the mirror image of the collision on Routing, and
exactly as invisible. A test asserts that the whole of Settings renders **zero** pointers.

### The text pass and the touch pass, and what they actually found

Run as sweeps over every screen that is still reachable, after the plan review and the confirmation
window were put on the bench. Most of the work had been done by the screens' own rebuilds, so this
records what was left, including the two places where the sweep decided **not** to cut.

**Twelve dictionary entries were dead** — strings for screens that no longer exist, left behind when
those screens were replaced. A dictionary is the translation surface: an entry nobody renders is a
paragraph somebody would have translated, and there is no rendering that would have revealed it.

**One card title was four words.** *What these rules produce* became *Final rules*, which is what the
block shows — the rules after the anchors expand, in match order.

**One consequence existed only under a pointer.** *Export with secrets* does not say that the
credentials leave in clear and that the device writes the act to its event ring, and nobody guesses
either. It was a `title` on the button, which is to say it was written down in the one place a phone can
never show it. It is a sentence beside the controls now, and a test asserts both halves: the sentence is
on the page, and the button carries no tooltip that could quietly become the only copy again. The
disabled Apply button on the plan review lost its tooltip for the same reason — its reason is already a
panel at the top of that review, in full sentences.

**Where the sweep stopped.** The long prose on the plan review and the confirmation window stays. Rule
4 says a consequence belongs in the control that causes it rather than in a paragraph above it — and on
those two surfaces the paragraph *is* the control's consequence, read by somebody deciding under a
countdown whether to keep a change that may have taken their own connection. "It changes addressing, a
radio, or which interface is which" is not an explanation of the design; it is what the reader is
agreeing to. The same applies to the three screens that say what they cannot answer: the refusal notice
on Network, the tunnel-health blank on Status, and the empty-journal notice on Events. Each is long
because a blank in its place reads as an answer.

**Nothing on a live screen depends on hover.** Row actions are always drawn, reordering is two buttons
rather than a drag, and the only remaining `title` is the full text on a truncated long value — which
has a copy control beside it, so the tooltip is an addition rather than the only way in.

### Where the panel answers, and where it should: the reading and the setting are now on one screen

`ManagementReach` — whether the panel also answers on the network this device is a *client* of — was
reachable only from the profile editor, which Epic E deletes with the tunnel editor. Two designed
controls were about to lose their only route, which is the defect this epic removes arriving through the
removal itself. It moved to **Network**, directly under the rows that say which interfaces the panel
answers on today: the reading and the setting are halves of one question, and the person who has just
read where the panel answers is the person deciding where it should. The leak policy — *what happens
when a tunnel fails* — is the other one, and it travels with the tunnel editor in E6, because that is
the screen its question belongs to.

Network therefore edits the profile now, and it carries the save, review and apply bar from
`lib/editing.ts` — the same hook Routing and Settings use. A second mechanism for the same act is the
duplicate-control defect one floor up.

**The move cost one layout defect, found by the bench within a minute of the control landing.** The
switch was stamped with its pointer through `Field`, and the global `input { width: 100% }` — written
for the controls a value is typed into — stretched the checkbox across its grid column. At 360 px on
Chrome 153 that reported content wider than its own box on three nested elements, about 4 px each, which
is how a page starts scrolling sideways. A checkbox now keeps its intrinsic width. The 44 px floor
stays, because the floor is about the target and not about the paint.

### Deleting a profile takes two taps, and the second one refuses to be the first

A destructive act with no undo should not be one tap away — the same reasoning that keeps factory reset
out of the API. But "the button becomes *Delete for good?*" has a defect of its own that has to be closed
in the same change: **a double tap is an ordinary movement on a phone.** It is how people zoom and how
they recover from a tap they think missed, and a two-step control with no floor between the steps is
answered by one gesture, with the reader never seeing the second label.

So the confirming state refuses anything arriving within 500 ms — above the ~300 ms that defines a
double tap on every platform that has one, and far below the time it takes to read a name. And the
confirming label **names the profile that will disappear** rather than saying "for good", because
somebody who has tapped one row lower should find that out from the label and not from the result.
There is no help sentence beside it; the name has already said everything a sentence would.

Three mutations, each caught: no floor → the second tap deletes at +200 ms; the first tap also firing →
deleted with no confirmation at all; and the ordinary path → deleted at +700 ms, as it should.

### The parity manifest: `apps/ui/parity-manifest.json`, derived and never written

Generated by `apps/ui/src/parity.test.tsx`, which renders every screen against the extreme fixtures,
waits for each one's **data** rather than its frame, and reads every `data-pointer` out of the DOM.
Numeric segments become `-`, so the file is about positions in the document rather than about a
fixture's rows: two rules are not two covered fields.

```json
{
  "generatedBy": "apps/ui/src/parity.test.tsx — derived from the rendered DOM, never edited by hand",
  "screens": ["status", "clients", "events", "network", "routing", "settings"],
  "fields": [{ "pointer": "/routing/rules/-/action/outbound", "screen": "routing" }]
}
```

**An entry is a pointer and the screen it lives on**, sorted by pointer first. That ordering is what
makes the second question askable: the same pointer on two screens is two adjacent entries, and a
control duplicated across screens is one of the four defects this epic deletes. `screens` lists every
screen that was harvested, including the ones that edit nothing, so a consumer can tell *this screen has
no editable fields* from *this screen was not looked at*.

**Corrected 2026-09-21.** This paragraph used to say the test writes the file first and compares
second, and gave a good argument for it: the file on disk is then always the truth about what the
interface renders today, so the diff is in the working tree with the pointers named. The argument was
right and the order was a hole. A write that happens *before* the comparison makes the second run
green with no code change — measured by deleting the `ssid` field: two failures on run 1, one failure
and three passing on run 2, because run 1 had rewritten the file it compares against. For a pointer
the parity comparison separately requires, that still fails every time; for the container pointers
and every leaf marked `generated`, `device`, `catalogue` or `subscription`, a deletion failed once
and was green forever after. **A guard that rearms only when somebody remembers is not a guard.**

So the committed manifest is not touched on a mismatch. The harvest is written beside it as
`parity-manifest.actual.json`, the failure names both files and the `git diff --no-index` that shows
the difference, and accepting a change is an act — `WAYFARER_ACCEPT_MANIFEST=1` — rather than the
side effect of having run the tests twice. An **absent** manifest is still written and still fails:
there is nothing to disarm on a first run, and a reader left with a failure and no file to look at is
worse off.

Two further properties are asserted separately: that the harvest found **anything at all**, because
every screen breaking at once produces an empty harvest and an empty harvest agrees with a manifest
saying the interface edits nothing; and that a pointer which rendered with **no control** is named as
such rather than silently dropped, because "this field became a caption" and "somebody deleted this
control" read identically in a diff and need different answers.

#### A `data-pointer` is not a control, and the harvest believed it was

The harvest used to be every `[data-pointer]` in the rendered DOM. That answers *was this pointer
stamped onto something that rendered*; parity asks **can a person supply this value**. Measured
2026-09-21 by substituting the Wi-Fi passphrase's `SecretField` with a `div` carrying the same
pointer and a `span` holding the word *Passphrase*: six files, 113 tests, the parity comparison among
them — all green, with the credential the daemon refuses to activate a profile without rendered as
inert text. Deleting the same block fails by name, which is precisely why the gap survived: the check
failed on the obvious mutation and passed on the one somebody would commit.

A pointer counts now when the value can be supplied, proved three ways and declared none:

* a control that holds it — an `input`, `select`, `textarea`, `contenteditable`, or an element
  wearing one of ARIA's value roles, enabled, not read-only, not out of the tab order;
* a control **one tap away**, which is what a credential the device already holds looks like. Five
  positions on the extreme fixtures are in that state, so a gate that stopped at "is there an input
  right now" would have produced five false reds — and a false red is always answered by weakening
  the check. Accepting the button instead would reopen the hole one door in, so the button is tapped
  and the question asked again;
* a **choice made by pressing one of several buttons**, which is how `/tunnels/-/protocol` and
  `/routing/rules/-/kind` are filled. Nothing in the markup separates that from a decorative row, so
  the markup is not consulted: the button is tapped and the *document* is compared, and a tap that
  writes a position of this shape has proved what an attribute only claimed.

A block that contains other pointers is a **container**, and is neither tapped nor counted. The first
version tapped the first button in any block with no control, and the buttons inside `/uplinks`,
`/subscriptions` and `/routing/ruleSets` are Remove: every one of those rows left the draft and
twenty-seven required positions vanished with them. Five container pointers left the manifest in the
same change, which is the correction — a position in the document is not a thing a person fills.

What it does not claim: this is the interface half only. Whether every field a person must fill is
reachable from both the interface and the API is E7, asserted over the schema.

### The tunnel editor: three designed screens, and the three fields that never had a control

This is the screen the epic exists for. The owner's sentence that started it — *you literally have to
write commands for launching daemons into the config for every tunnel; that is code too, and it is not
friendly* — was about a text field wanting a command line with flags beside another holding an entire
client configuration as a string, where a wrong flag failed silently.

**One designed editor per catalogue entry, three of them, each named for what the owner holds.** An
`.ovpn` file. An `.ovpn` file plus the entry points that front it. A link or a subscription. Never for
the program this device starts: the entry called `Xray` was renamed when the owner asked why, since Xray
is merely what runs his VLESS subscription, and the consequence is not a rename. Because the entry is
named for the thing rather than for the runner, **which program carries it is not a question he can be
asked** — the entry establishes it from the configuration and states the choice in the plan. So there is
no control for it and no sentence on the screen mentions one; a test asserts that the rendered text names
no program, over the DOM rather than over the source, because a sentence in a component nobody mounts is
not on the screen and a grep cannot tell the difference.

The editors are joined to the catalogue **by the compiler**: `EDITORS` is a total map over
`TunnelProtocol`, so an entry added in Epic F without a screen does not build. That is the same mechanism
the schema uses for its own two halves, applied to the third half that lives in the browser.

**`resources`.** What the tunnel exists to reach, at `/tunnels/-/resources/domainSuffix` and `/ipCidr` —
the same words a routing rule uses at a different pointer, which is how this half stayed invisible long
enough to make the product API-only. The address ranges are not a convenience beside the names: a name
rule matches only a name the device recovered by sniffing, so a connection to a literal address or one
whose name is encrypted falls past every suffix in the list. That is stated in the control's own help
sentence. Drawn for a `resource` tunnel only, because that is the only role `tunnel-resources` expands.

**`probe`.** What to fetch *through* the tunnel. The device-wide probe list fetches something on the
public internet, which is right for a tunnel whose job is egress and wrong for one that reaches only
internal resources — measured on the bench board, 2026-09-21: the corporate tunnel's guard fails an
internet probe while the tunnel is healthy, because that peer pushes only private routes. **An empty probe
is a state the control says out loud**: nothing is measured, health stays unknown, the watchdog will not
move in either direction. Measured the same day, on the same board: a tunnel with no probe had a guard
that could never fire while a fallback judgement reported it healthy for an hour. A blank there reads as
health. Written at the parent pointer rather than at the list, because `endpoints` has a minimum of one
and a probe holding an empty array is a document that cannot validate.

**The obfuscation entry points.** Several per tunnel — the bench's corporate tunnel has four, at four
sites, each pretending to be a different domain. Every field is its own control and the credential among
them is marked; five of those identifiers reached a *redacted* export in clear because they lived inside
one unmarked string and nothing ever descended into the list. The order is the order of the generated
`remote` lines, so reordering is an edit, done with two buttons rather than a drag.

**`LeakPolicy` moved here**, because what happens when a tunnel cannot carry its traffic belongs on the
screen about tunnels — and the person deciding it needs the list of tunnels it is about directly above.
`firewall.ntpBypass` sits beside it for the same reason: it asks the same question, may something leave
outside a tunnel, and its consequence is specific to this board, which has no clock battery.

#### The paste box and the feed are two different acts, and never share a word

The VLESS editor takes a link and fills one tunnel, once, through **the parser the daemon already uses**
— `parseSubscription` from `@wayfarer/protocols`, which returns the protocol-and-configuration pair and
refuses by naming both halves. A refusal is printed **verbatim**; its whole value is that it says which
scheme was not accepted *and* which three are, and a paraphrase keeps the first and loses the second.

A **subscription** is stored and re-read on a schedule, and every refresh rewrites the tunnels it owns.
Its fields — name, URL, enabled, refresh interval — had no editor anywhere, and that was found by the
mechanical parity check rather than by a person. Same shape as the three fields above: **not a field
somebody decided to hide, but a field whose editor was never written, because no task owned the screen it
belonged on.** It is on this screen because a subscription is *where tunnels come from*; in Settings it
would be a list of URLs explaining nothing. Each feed says how many of the tunnels above it made, which is
the other side of the badge on a tunnel row.

### Deleting a screen must enumerate what else lived on it

`pages/ProfileEditor.tsx` was deleted here with the generic form, the overlay and the JSON escape hatch.
Checked before deleting, by reading what the screen still rendered rather than by reading the plan:
**thirty positions were reachable from it and from nowhere else** — the network name, the Wi-Fi
passphrase, the range of addresses handed to clients, the radio's band and channel, the uplink
credentials, the resolvers, the profile's own name. E10 put the access point and the uplink on Network;

Deleting without moving them would have left all of it reachable only through the API — **the owner's

access point, radio, uplinks, the local network with its address range, and DNS onto **Network**, each as
a fold under the card that already *reads* the same thing; the profile's name and note onto **Settings**.
The reading and the setting on one card is the same argument that moved `ManagementReach` there.

Two consequences recorded rather than left to be rediscovered. **Only the active profile is editable now**,
because every screen that edits reads `activeProfileId`, where the old editor took an id from the route —

That is a defect, it is owned by a task of its own, and the shape is agreed: the edited profile is

what it was written for.

### The parity comparison runs where the manifest is built

`parityReport` is called inside `src/parity.test.tsx`, against the object just harvested from the rendered
DOM — never re-read from the file. The comparison could have lived in the daemon's run, beside the schema
half, and must not: that run would read the manifest from disk, so a **stale** file fails towards the
reassuring answer and a control deleted from a screen stays green. Detecting staleness would be one more
thing that can silently fail; comparing in the same run removes the possibility. The file on disk stays
for a person to read and a diff to show.

### Two fields on every role, and why neither is a checkbox

`pinName` and `takeOverInterface` are the last two positions the interface had no control for at all,
and they arrived through the parity check rather than through anybody's reading. The reason they were
invisible is recorded in [16](16-implementation-notes.md): the requirement walk memoised on object
identity, and `HardwareBinding`, `PinName` and `TakeOverInterface` are **one declaration shared by two
roles** — so the access point's four positions were never walked, were never required, and the screen
that was ported against that list could not have included them.

The reflex control for a boolean is a checkbox, and it is the wrong shape here. A checkbox has one
label, so only the *on* answer can carry a sentence, and leaving it clear is then the answer nothing
explains. For both of these **off is a decision with a consequence of its own**:

* **Interface name.** Left alone, the role uses whatever the kernel calls the interface, applies with
  no reboot, and may be numbered differently after a dongle is moved. Pinned, the role gets a
  deterministic name — and the rename needs the link down, so it takes effect at the next boot and can
  cost the session it arrives over. That is why it belongs in a second change, after the first is
  confirmed: bundling the irreversible rename with everything else means that if the device does not
  come back, nobody can tell which half did it.
* **If already claimed.** Left alone, a plan that finds another manager configuring the interface
  **stops and names the file** — measured in `invariants.ts`, which raises `interface_claimed_elsewhere`
  as an error rather than a warning. Turned on, the claim is cleared during the apply: the file is
  moved aside, never deleted, and a revert inside the confirmation window puts it back.

So both are drawn with the radio group `ChoiceField` already uses for the leak policy — two answers,
each with its sentence beside it — rather than with a checkbox and a tooltip. `BooleanChoiceField`
shares that renderer instead of copying its markup, because the copy is the one that would not get the
next fix to the 44 px target or the radio's width.

The sentences are written once and used by both roles, for the same reason the schema marks the source
on the declaration rather than at each use: the access point's rename and an uplink's rename are the
same act, and two copies are two copies that drift.

**The hazard the shared renderer introduces, and the test for it.** A radio input's own value is always
a string. Reusing the control that edits string-valued choices invites writing `"true"` into a position
the schema declares as a boolean — a document that looks right in the panel and is refused on save. A
test asserts the written value is a boolean, and it was proved by mutation: substituting
`event.target.value` for the option's own value makes it fail and leaves the string-valued control
green.

### A control that existed, and had never been rendered by anything

`/routing/rules/-/sets` was on the same fault list as the four above, and it was not a missing control.
The list of rule-set tags is drawn for `kind === 'ruleSet'` and **the extreme fixture had no rule of
that kind** — five kinds and both anchors, and not that one. So the control left the DOM, left the
coverage manifest and left the 360 px measurement, with every check green and the field reported as
one the API can set and no screen shows.

Same shape as the bench answering `{}` for `/api/fleet` and as a document with no feeds and no uplinks:
**a branch a fixture never reaches is a branch nothing measures**, and the interface half of the parity
check cannot tell it apart from a control nobody wrote. It is one rule in the fixture now, and the
pointer reappeared in the manifest the moment it was added — which is the measurement.

### The parity check reached zero, and none of the twenty-seven was excluded to get there

The interface half of the check reported **119 positions must be fillable, 92 render**. The twenty-seven
faults were three different defects wearing one message, and each needed a different answer.

**Two were fillable and unstamped.** `/tunnels/-/protocol` and `/routing/rules/-/kind` are chosen when a
row is added, by a control that carried no pointer. The tempting answer was to exclude them in the
schema — a tunnel's protocol is not *edited*, after all — and it would have been a lie told to make a
check quiet. A person genuinely chooses between three catalogue entries and between five rule kinds; the
source annotation records **where a value comes from**, not which shape of control supplies it. A choice
made by pressing one of three buttons is still a choice, so the add control carries the pointer. The
comment in `Tunnels.tsx` that listed `protocol` among "three positions with no control" was wrong in its
reasoning rather than in its conclusion, and it says so now: it is a field filled once, not a field
nobody fills.

Adding `/routing/rules/-/kind` to the add control also exposed that `ruleSet` was the one kind the
control could not produce, while the rules screen described it and a help sentence named the sets it
matches. A kind that can be referenced and not created is the same half-built shape as a rule set with no
editor, and both landed together.

**Seven were small missing controls** on the uplink — `enabled`, and the address, gateway, resolvers,
band, BSSID and hidden flag. They are folds on Network beside the rest of the uplink.

**Twenty-four were whole sections with no screen**: the failover policy and its eight probe thresholds,
the firewall's blocked endpoints and its IPv6 setting, the rule sets, and whether the core's control API
runs at all. None of them got a screen. The policy and the probes are folds on **Tunnels**, on the card
that already answers what happens when a tunnel fails; the firewall's two are a card on **Network** about
what may leave this network; the rule sets are a card on **Routing** beside the rules that name them; the
control API is in the Device fold on **Settings**. A screen called *Failover* would have been an eighth
screen answering half of a question Tunnels already asks, and the person deciding a threshold is the
person reading the tunnel list directly above it.

**Why none of this was deferred.** A check that is permanently red for a known reason stops being read,
and is then worth nothing on the day it is right. The epic's claim is that nothing is configurable in one
place only; twenty-four positions reachable from the API alone are that claim's contradiction, written
down and green.

### One object, two questions, and the split follows the question

`FirewallConfig` has four fields and they are on two screens. `killSwitch` and `ntpBypass` are on
**Tunnels**, because what they answer is *what happens when a tunnel cannot carry the traffic*. `ipv6` and
`blockedEndpoints` are on **Network**, because what they answer is *what may leave the network this device
serves* — the same question as the address range and the resolvers beside them.

Keeping an object together would have been the tidier rule and the wrong one. The screens in this
interface are organised by the question a person arrives with, and `firewall` is a name for where four
answers happen to be stored.

Two of these say less than they look like they say, and both sentences are in the control rather than
above it. `ipv6` has exactly one legal answer, `block`; a select with one option looks like an oversight,
so the sentence states that this is the answer the device has and why it is a rejection rather than merely
leaving IPv6 unrouted. And a blocked endpoint with a **domain** becomes a reject rule in the proxy core's
routing rather than a firewall rule, so it does nothing for a client connecting to a literal address it
resolved somewhere else — which is the single most misleading thing on that card.

### A choice that can be left unanswered, and the two spellings of "unanswered"

`SelectField` grew one option for **not answering**, because several of these fields are optional in a way
that means something: a Wi-Fi uplink with no band joins on whichever band the network is on, and a rule set
with no format is read by its file extension.

The reflex implementation is an empty `<option>`, and it writes `""` — which is in neither half of either
union and is refused on save, after the panel has shown a document that looks correct. So the option
carries a distinct value and the control carries **which absence to write**: `band` is a union with `null`
in it, and `format` is `Type.Optional`, which is the absence of a key. They are not interchangeable and the
same validator refuses either one in the other's place.

The test for it asserts `'band' in config` rather than that the value is falsy, because a written `null`
and an absent key are the same falsy reading and a test on truthiness passes on the bug.

### E6b: the profile being edited is chosen, and the bar offers Save only when it is not running

Deleting the old profile editor left the four editing screens working on the active profile alone. The API
could edit any stored profile and the interface exactly one — the asymmetry this epic exists to remove,
pointing the other way — and preparing an alternative meant activating it, which is the step before
applying it.

**The selection lives in a store, not in a route.** A person preparing an alternative moves between
Tunnels, Routing and Network while preparing it, and a per-screen route parameter would silently put them
back on the active profile at every navigation — which is this task's own defect wearing a different hat.
A chosen id that is no longer in the list resolves back to the active profile rather than to nothing:
four screens loading a document for a profile that does not exist render as a screen that is still
loading and never stops, which looks exactly like a slow device.

**The shell says which profile it is, and only when it is not the active one.** In the shell rather than
on the screens, because the hazard is precisely that a person does not remember: the choice is made on
Settings and survives every navigation, so a warning on the screen where the choice was made is absent on
the four screens where the editing happens. Drawn only in the non-active state, because a banner that is
always there is a banner nobody reads on the day it changes.

**On a profile that is not active the bar offers Save and Discard, and applying is unreachable until the
profile is activated.** This is the decision worth keeping the reasoning for. The confirmation window's
entire safety property is an operator watching a countdown on the device being changed: the device
applies, waits, and undoes itself unless somebody who can still reach it says otherwise. A profile that is
not running has no plan against reality, no blast radius and therefore no window — so a button labelled
"review and apply" here would blur **activating** with **applying**, which are two different acts, and a
first-time user is already on record reading one as the other. Review is absent rather than disabled, and
the sentence beside it names the step that has not happened; a disabled control with no explanation reads
as a fault in the panel.

**Switching while an edit is unsaved is refused, and the refusal names the reason.** Switching replaces the
draft, and a replacement is a silent loss. The chooser says *Save or discard first* rather than being a
control that quietly does nothing — the same shape as the plan that stops and names the file rather than
writing over another manager's interface.

**Picking the active profile clears the selection rather than storing its id.** Stored, the id would go on
pointing at a profile that stops being active the moment somebody activates another, and the screens would
edit it while the shell said nothing — this task's defect, reintroduced by the control that fixes it.

The bar itself is now one component. Tunnels, Routing and Network each carried a copy of its markup, which
was already the duplicate-control defect one floor up, and the rule above would have had to be written into
all three.

### The one place a long value is wrapped rather than truncated

Rule 6 says long values never break the layout, and everywhere else the remedy is truncation with a copy
control. The notice naming the profile being edited is the exception, and the exception is principled: the
rule is about values whose meaning a break destroys — an address split across two lines reads as two
addresses, a fingerprint broken anywhere reads as a different fingerprint. A profile's **name** is a label
nobody retypes, and truncating it would hide which profile is being edited, which is the entire content of
the sentence.

It is `overflow-wrap: anywhere` rather than `break-word`, because a 64-character name with no space and no
hyphen in it — which is what people actually type — has no break opportunity at all, and `break-word`
leaves it whole and overflowing. Measured on the 360 px bench, 2026-09-21: the first draft of this notice
made the page **504 px wide at a 360 px viewport**. The bench found it, which is the second time this week
that the thing which caught a defect was a fixture holding the value nobody would have chosen by hand.

### A fourth tunnel screen, and the one control the bench proved was never measured (2026-09-22)

`Proxy` is the fourth designed screen, and it is one screen for three answers rather than three
screens differing by a dropdown: the person picks what his provider told him it speaks, and the
handshake name and trusted certificate are drawn for HTTPS and for nothing else. Each of the three
choices carries its own consequence sentence — whether the hop to the proxy is encrypted, and whether
UDP can cross it — because that is the difference between them and it is not a word anybody can rank.
There is no box that turns certificate checking off, and a test asserts its absence.

The fixture had to grow with it. Protocols are dealt round the sixteen tunnels by
`index % protocols.length`, so adding a fourth moved every tunnel's protocol along and the Reality
VLESS tunnel stopped being a VLESS tunnel at all. **The parity harvest caught that**, by name:
`realityPublicKey` and `realityShortId` went from fillable to not, in the same run that added the
three new proxy pointers. A manifest read off a rendered DOM is the only kind that could have.

**And the bench caught a defect in itself.** `GET /api/drift` had been unanswered by `extremes.tsx`
since the Status panel started asking for it, so `check:360` had been failing on that route and the
panel it feeds had never been measured at any width. That is exactly the failure the unanswered-route
list was added to catch — a fold whose query is unanswered renders empty, an empty fold fits inside
360 px, and every measurement below it is true of nothing. Both routes now have fixtures carrying the
longest wording each can produce.

### The age of a rule set, on the row that names it

A rule set's row on Routing now carries how old this device's copy is. Three pills and five states,
and the mapping is the argument: `overdue` and `never-fetched` are red, because traffic a rule was
written for is leaving by the ordinary route right now; `unmeasurable` and `no-cadence` are amber
rather than silent, because neither is a fault in the list and rendering either as fine would put a
reassuring colour in front of somebody in exactly the case where nobody knows; `fresh` is the only
green, and it is green because a number was computed.

The sentence under the pill is the device's own wording and is never omitted. A colour alone is
something a person learns to stop seeing, and a blank where a measurement belongs reads as health —
the same finding as the empty probe, one screen along.

Nothing on this screen subtracts two timestamps. The browser's clock is a third clock, the board's
has no battery, and the decision about when an age can honestly be computed is argued once on the
daemon's side. The only arithmetic here turns a number the device already stood behind into words.

Rule 4 took the last of it: **the refresh-interval field says what leaving it empty costs** — *"Hours;
left empty, nothing can report this list as out of date."* That is the one consequence a person
cannot discover any other way, because its symptom is a check that never fires.

### What review found on the two screens above, 2026-09-22

Three of the four were the same shape: **a control that hides a field does not remove it, and a
screen that shows a number does not own it.**

**The proxy editor produced a refusal a person could not clear.** Fill in a certificate on HTTPS,
switch the type to SOCKS, and the two TLS controls disappear while the draft keeps their values —
so the plan is refused pointing at `/tunnels/-/config/tlsCertificate`, a position with no control
on any screen. The editor now clears both when the type stops being HTTPS, through an ordinary
draft write, so the clearing joins the same pending change as the choice that caused it and Review
shows both. That is the general rule for a conditional field: **whatever draws it conditionally owns
clearing it.**

**Two formatters for one age had already drifted.** The pill divided seconds in the browser and the
sentence beneath it printed the device's wording, and the two switched from minutes to hours at
different thresholds — a row read `1h` above `83m ago`. The device now sends `ageLabel` beside
`ageSeconds` and the screen prints it. Nothing here subtracts or divides a time: the browser's clock
is a third clock, and the decision about whether an age can honestly be computed at all was already
argued once on the other side.

**A remote set's figure is a lower bound, so the pill says `≥ 4d`.** It is the age of the shared
cache, which is the most recent write by any set in it — a figure that understates. Drawing it as a
plain duration is a measurement this device cannot support, and it is the number a person would
quote.

**And the ages are drawn only when the profile on screen is the one the device answered about.** The
device answers for the **active** profile, because the ages describe files it actually holds; the
join to a stored set is a tag string, so a not-yet-applied profile reusing `geoip-ru` was being shown
the running profile's freshness for a list this device may never have fetched. The response carries
`profileId` and the screen compares it, saying nothing rather than something reassuring.

The fourth was in the bench again, and in the same commit that fixed it: `index === 3` and
`index === 7` picked the HTTPS and HTTP proxies, and both were correct only because there happened to
be four catalogue entries. Every special case in that fixture is now pinned to the tunnel's **ordinal
within its own protocol**, so a fifth entry cannot silently take a rendered control out of the
manifest and the 360 px measurement.
